# ADR 0002 — ارزیابی Cloudflare برای Backend همراه‌یاب

- **وضعیت:** پذیرفته‌شده برای نمونه اولیه و مرحله آزمایشی؛ مشروط به آزمون عملی دسترسی از ایران.
- **تاریخ:** 2026-11-26

## زمینه

همراه‌یاب به API کم‌هزینه و مستقل از ارائه‌دهنده Push نیاز دارد. استفاده از Firebase به‌عنوان وابستگی اجباری مناسب نیست؛ دسترسی و تحویل Push باید روی دستگاه‌ها و شبکه‌های واقعی بازار ایران آزمایش شود.

## تصمیم

Cloudflare Workers به‌عنوان لایه API و D1 به‌عنوان ذخیره‌ساز اولیه metadata انتخاب می‌شوند. این انتخاب فعلاً برای MVP و بار کم است، نه تضمین معماری نهایی. منطق دامنه و قرارداد API مستقل از Cloudflare نگه داشته می‌شود تا مهاجرت به سرور داخلی یا PostgreSQL ممکن باشد.

## مزایا

- اجرای API بدون مدیریت مستقیم ماشین مجازی.
- HTTPS و لبه توزیع‌شده.
- D1 برای داده رابطه‌ای سبک MVP.
- امکان افزودن Queue برای پردازش رویداد و adapterهای Push.
- عدم نیاز به توکن Cloudflare در برنامه Android.

## محدودیت‌ها و ریسک‌ها

- دسترسی پایدار از اپراتورها و شبکه‌های داخل ایران باید واقعاً تست شود؛ از روی نام سرویس نمی‌توان دسترسی را تضمین کرد.
- سرویس پیامک OTP و Push بومی/جایگزین باید جداگانه ارزیابی شوند.
- D1 برای رشد بالا یا queryهای پیچیده ممکن است محدودکننده باشد؛ migration path به PostgreSQL حفظ می‌شود.
- Worker نباید به‌تنهایی مکان‌یابی پس‌زمینه را تضمین‌شده جلوه دهد؛ محدودیت‌های Android و Doze پابرجاست.
- هزینه‌ها، سقف درخواست/ذخیره‌سازی و شرایط جاری Cloudflare قبل از production دوباره بررسی می‌شوند.

## امنیت و عملیات

- هیچ secret در Git یا APK ثبت نمی‌شود.
- توکن‌ها و کدهای یک‌بارمصرف به شکل hash ذخیره می‌شوند.
- موقعیت دقیق فقط پس از بررسی server-side consent و درخواست معتبر ارسال/بازگردانده می‌شود.
- Push فقط wake-up event opaque است.
- در MVP فقط آخرین موقعیت مجاز نگهداری می‌شود؛ تاریخچه مکانی پیش‌فرض وجود ندارد.
- staging قبل از production، rate limit، audit و deletion policy اجباری است.

## پیامد

در این مرحله فقط schema و قرارداد API آماده می‌شود. استقرار Cloudflare پس از تأیید دسترسی، انتخاب providerهای OTP/Push و دریافت secret محدود از مالک حساب انجام می‌شود.
